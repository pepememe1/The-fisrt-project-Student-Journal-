## Глава 1. Sync Fabric — что именно откладывается и почему

Ярослав сам расставил этапы и риски, и с ними я согласен без оговорок:

| этап | суть | риск по плану | статус |
|---|---|---|---|
| 0 | спецификация Sync Protocol v2 и матрица инвариантов | низкий | **делается** (см. ниже) |
| 1 | `base_revision` и структурированные конфликты для оценок | средний | не начат |
| 2 | `SyncProjectionRegistry` и contract-тесты прав/полей | средний | не начат |
| 3 | локальный durable `sync_ops` journal | **высокий, отдельный релиз** | не начат |
| 4 | `sync_changes` + opaque cursor + `resync_required` | **высокий, отдельный релиз** | не начат |
| 5 | SSE wake-up и privacy-safe diagnostics | низкий после v2 | не начат |

🔥 **Почему нельзя начать с этапа 3 или 4, хотя именно они чинят самое больное.**
Локальный журнал операций обязан создаваться В ОДНОЙ ТРАНЗАКЦИИ с бизнес-правкой — иначе
он «почти работает», а это худшее состояние для синхронизации. Ярослав пишет об этом
прямо: «ручное добавление из нескольких UI-путей неизбежно когда-нибудь пропустит
изменение». У нас записи в локальную базу идут из десктопа, офлайн-очереди веба и
слияния с сервера; свести их в один write boundary — это и есть отдельный релиз, а не
часть захода по багам.

### Матрица инвариантов (этап 0) — то, что обязано остаться истинным при любом протоколе

Формулировка Ярослава: «оценка либо применена один раз, либо явно в конфликте; никогда не
исчезла и не изменилась молча». Разворачиваю в проверяемые утверждения:

1. **Идемпотентность.** Повтор доставки одного `operation_id` не создаёт второй записи и
   не меняет результат. (Сегодня частично есть: `client_nonce` в мессенджере, `push`
   идемпотентен по содержимому.)
2. **Ни одной потерянной правки.** Падение процесса между локальной записью и отправкой
   не теряет операцию. (Сегодня НЕ выполняется: `_push_watermark` двигается по времени.)
3. **Конфликт заметен.** Расхождение значения оценки не разрешается молча в пользу
   последнего. (Сегодня выполняется наполовину: `_merge_grades` пишет в `sync_conflicts`,
   но **разбирать их нечем** — диалог удалён вместе с Qt, и `list_conflicts` не зовёт
   никто. Это записано в самом коде и остаётся честным долгом.)
4. **Причинность объяснима.** Про любую правку можно сказать, кто и на каком устройстве
   её сделал. (Сегодня частично: `Grade.device`.)
5. **Роль не расширяется синхронизацией.** Через `/sync/push` нельзя записать то, чего
   роль не может записать через веб. (Сегодня выполняется, держат тесты `test_sync.py`.)

⚠️ **Что из плана я СОЗНАТЕЛЬНО не рекомендую даже в будущем** — и Ярослав тут прав
дословно: CRDT для оценок («4» и «5» не сливаются), P2P/WebRTC, внешний replication-сервис
(Electric/PowerSync), WebSocket как основа надёжности.

## Глава 2. База данных — что делать и в каком порядке

Ключевая мысль плана, с которой надо начинать: **«индексировать всё» не оптимизация**.
У нас ОДИН writer, и каждый лишний индекс делает запись тяжелее.

| пункт | статус | почему так |
|---|---|---|
| read-only диагностика (версия SQLite, WAL, page_count, freelist) | **сделано** | дёшево, ничего не меняет, сразу отвечает на «а что там вообще происходит» |
| проверка версии SQLite против 3.51.3 (WAL-reset гонка) | **сделано** | эксплуатационный контроль, не авария |
| синтетический датасет + p50/p95 + `EXPLAIN QUERY PLAN` в CI | не начат | нужен отдельный стенд; без него составные индексы добавлять НЕЛЬЗЯ |
| составные индексы из таблицы плана | **не добавлены намеренно** | план сам требует «только после EXPLAIN». Добавить «на веру» — ровно то, от чего он предостерегает |
| Schema Ledger вместо списка `_ensure_*` | не начат | наш нынешний способ работает и покрыт регрессиями; менять его без нагрузки — риск без выгоды |
| «не держать writer во время сети» (принцип Convex) | частично есть | у нас уже вынесены в пул потоков Whisper, перевод, приманки; отдельного правила нет |

## Глава 3. Безопасность — построчно

| Ed25519-подпись обновлений, публичный ключ в desktop/APK | **не сделан** | нужен **offline-ключ**, которого у меня нет и который нельзя генерировать на рабочей машине. Недоделанная подпись хуже её отсутствия: она создаёт уверенность. Нужно решение Ярослава, где живёт приватный ключ |

## Что я предлагаю следующим заходом

1. **Authorization fuzzing matrix** — чистые тесты, нулевой риск, закрывает самый частый
   класс уязвимости API (BOLA). Лучшее соотношение пользы к риску во всём плане.
2. **systemd hardening в `deploy/install.sh`** + проверка `systemd-analyze security` —
   касается будущей машины ВСГУТУ, живой юнит не трогает.
3. **Стенд для замеров** (синтетический датасет + `EXPLAIN QUERY PLAN`) — без него глава 2
   не двигается вообще.

## Что требует решения Ярослава, а не работы

* где живёт **offline-ключ подписи** обновлений (без ответа пункт P0 не начать);
* какое **внешнее хранилище** для WORM-бэкапа и audit anchor (закупка);
* минимальная **длина пароля** для входа без второго фактора — 15 символов ломает вход
  существующим людям, это решение продукта, а не техники;
* **passkey у администратора** — прямо конфликтует с только что снятым вторым фактором.
