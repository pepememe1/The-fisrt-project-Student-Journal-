## 12. Миграция оценок с ФИО-ключей на `student_id` (СОСТОЯНИЕ)

Зачем: оценка ключевалась по НАПИСАНИЮ ФИО. Студентка выходит замуж, админ правит
фамилию — вся история остаётся на старом ключе. id строки `users` не меняется никогда.

| Этап | Что | Статус |
|---|---|---|
| 0 | id студента стал неизменяемым (`stud:u:{uuid4}` вместо ФИО-производного) | ✅ |
| 1 | добавочная колонка `student_id` в `grades`/`term_grades`, транспорт синка | ✅ обе платформы |
| 2 | бэкофилл существующих строк | ✅ прод 47/47; десктоп доклеивает сам после синка |
| 3 | переключение ключа на `student_id` | ✅ СЕРВЕР · ✅ ДЕСКТОП (`0fe2b6f`, 19.07.2026) · ⚠️ прод НЕ ПРОВЕРЕН |

**Что осталось (важно, не потерять):**
- ⚠️ **ЗДЕСЬ ПОЛТОРА МЕСЯЦА СТОЯЛА НЕПРАВДА** (поправлено 31.08.2026). Значилось
  «❌ ДЕСКТОП» и «десктоп ещё ключует `term_grades` по ФИО» — на деле десктопная сторона
  закрыта коммитом `0fe2b6f` **19.07.2026**: `data/core.py::grade_id/term_grade_id`
  зеркалят серверные, переименование студента идёт UPDATE на месте (у живой строки и её
  надгробия один `student_id`, и надгробие похоронило бы живую оценку),
  `migrate_local_term_keys` переводит накопленные итоговые из `sync_runner` после
  бэкофилла. То есть пункт, который читался как «мина под выкатом», был закрыт до того,
  как его сюда записали как открытый.
- ❗ **Что действительно не проверено — ПРОД:** гонялся ли `migrate_grade_keys.py --apply`
  на боевой базе, по этому файлу сказать нельзя. Проверять НАДО на бою (`--apply` —
  точка невозврата, нужен свежий бэкап), а не по памяти. Пока не проверено — считать
  открытым именно этот шаг, а не десктопный.
- Порядок выката (для справки, две трети уже позади): **десктопная сторона → деплой
  сервера → `migrate_grade_keys.py --apply` на проде → пересборка exe**.

**Инструменты:**
- `server/backfill_student_id.py` — этап 2 на сервере (холостой прогон по умолчанию,
  `--apply` пишет, `--report` в файл). Печатает СПИСОК несклеенных ФИО с причинами.
- `tools/backfill_student_id_desktop.py` — то же для десктопа, диагностика.
  Сама логика — в `data/student_link.py` (попадает в .exe), зовётся из `sync_runner`
  после каждого удачного синка.
- `server/migrate_grade_keys.py` — этап 3, перевод ключей. ТОЧКА НЕВОЗВРАТА, нужен
  свежий бэкап. Останавливается на конфликтах вместо молчаливого слияния.

**Правила, которые нельзя нарушать:**
- Бэкофилл **НЕ трогает `updated_at`**. Бамп объявил бы каждую оценку изменённой (весь
  парк выкачал бы базу заново), а серверная метка могла бы перебить более свежую
  офлайн-правку. Из-за этого же дельта не привозит id на клиента — каждый ПК клеит сам.
- Студент не опознан (нет в справочнике / неразличимые тёзки) — **строку НЕ отбрасываем**
  и id НЕ угадываем. Ростер преподавателя ведётся отдельно, такие оценки законны;
  потеря данных несоразмерно хуже дубля, а «оценка не тому студенту» — хуже обоих.
- `_normalize_grade_key` в `server/app/routers/sync.py` пересчитывает ключ входящих
  оценок: старый клиент шлёт ФИО-ключ, и без этого строка легла бы РЯДОМ с новой.

**Бэкапы прода:** `/root/gb-backups/` на VPS + локально `WORK/GB_2_7/gb-backups/`
(ВНЕ репозитория). ⚠️ Архив содержит `.env` (ключ SQLCipher + JWT-секрет) — без него
зашифрованная копия бесполезна, но и в облако/git такой архив класть нельзя.
