## 7.1 Инструменты разработки — расширения VS Code (что, когда, как)

> Расширения поставил Ярослав (07.08.2026). Раздел фиксирует, **зачем каждое нужно
> ИМЕННО НАМ** и когда его звать — иначе через месяц никто не вспомнит, почему они
> стоят, и они превратятся в мёртвый груз в списке.
> 🔑 Правило то же, что у тестов: **инструмент, который шумит, перестают читать.**
> Поэтому каждый настроен на «ловить реальные проблемы», а не воевать со стилем.

### Mypy Type Checker (`ms-python.mypy-type-checker`) — 🟢 основной

⚠️ **ПЕРВОЕ, что нужно знать: по умолчанию расширение ИГНОРИРУЕТ наш allowlist.**
В `pyproject.toml` (`[tool.mypy]`) стоит осознанное решение — проверять только уже
типизированные модули (`files = [...]`, сейчас 5 файлов), чтобы проверка оставалась
ЗЕЛЁНОЙ, а не «1000 ошибок, все игнорируют». Но расширение в режиме по умолчанию
(`reportingScope: "file"`) передаёт mypy открытый файл ЯВНЫМ аргументом, а явный
аргумент перебивает `files` из конфига. Разница измерена:

```text
python -m mypy              →   3 ошибки  (5 файлов, как в CI)
mypy на весь проект         → 644 ошибки  (154 файла)
```

**644 ошибки — это не поломка, это непроверяемое легаси**, которое мы сознательно ещё
не типизировали. Лечится настройкой, НЕ правкой кода:
`"mypy-type-checker.reportingScope": "workspace"` в `.vscode/settings.json`.

**Когда зову:** перед сдачей правок в синк/сервер/`grading.py` и любой модуль из
allowlist — `python -m mypy` из корня (именно так, без аргументов: только тогда
действует `files` и результат совпадает с тем, что увидит CI).
**Как расширяем охват:** типизировали модуль целиком — дописали его в `files`.
Добавлять модуль «наполовину» нельзя: он утащит проверку в красное и обесценит её.

### ESLint (`dbaeumer.vscode-eslint`) — 🟢 основной для `web/`

Уже настроен: `web/eslint.config.js` (flat-config ESLint 9) + prettier поверх,
команды `npm run lint` / `lint:fix`. Состояние на 07.08.2026 — **1 ошибка, 9
предупреждений** (не потоп, довести до нуля реально).

🔑 **Почему это не формальность, а закрытие ДВУХ задокументированных классов багов,
каждый из которых уже стоил нам «пустой/сломанной страницы»:**

- **Грабли 3.4.1** (`watch()` читает `ref`, объявленный НИЖЕ по файлу — обращение из
  мёртвой зоны валит весь `setup`). В шапке этого файла про них написано «ни линтер,
  ни сборка этого не видят» — **это утверждение неверно**: правило
  `no-use-before-define` ловит ровно это. Тогда линтера просто не было.
- **Артефакт фоновых агентов** — лишний `</content>` после `</template>` в 4 файлах,
  уронивший `npm run build`. Ловится `vue/no-parsing-error` до сборки.

**Когда зову:** после любой правки в `web/src` — `cd web && npm run lint`. Обязательно
после генерации `.vue` агентами (см. граблю выше). Перед `npm run build`, а не после.

### Markdown lint (`DavidAnson.vscode-markdownlint`) — 🟡 вспомогательный

Документации у нас много (`CLAUDE.md`, `README.md`, `docs/*.md`), и README **публичный**
— битая таблица или сломанный список видны на GitHub покупателю.

⚠️ Без конфига в нём тонешь: на одном CLAUDE.md расширение выдало **107
предупреждений**, файл намеренно нарушает половину стилевых правил. Поэтому заведён
**`.markdownlint.jsonc`** (именно `.jsonc`, а не `.json`: комментарии официально
поддержаны, и каждое из 18 отключённых правил подписано — почему). Итог: **107 → 31**,
и все оставшиеся реальные.

Оставлены правила, которые **ломают рендер или являются опечаткой**: `MD032`/`MD031`
(нет пустой строки вокруг списка или блока кода — они слипнутся в абзац), `MD011`
(перевёрнутая ссылка), `MD040` (язык у блока кода), `MD042`, `MD047`.

⚠️ **`MD038` выключен как ЛОЖНОЕ срабатывание, а не как стиль** — 63 штуки из 107.
Проверено поимённо: пробелов внутри code-span'ов там нет. Правило спотыкается о ручную
вёрстку под ~95 колонок — длинный спан переносится через строку, и перенос считается
пробелом внутри. Если решишь снять глушилку — сначала перечитай это, а не начинай
«чинить» 63 несуществующие ошибки.

**Когда зову:** правил `README.md` или `docs/*` — проверить перед коммитом. README
**публичный**, битая таблица или сломанный список видны на GitHub покупателю.
Правило проверено на себе: этот самый раздел markdownlint поймал дважды (блок кода без
языка и список без пустой строки) — обе правки реальные, а не косметика.

### Container Tools (`ms-azuretools.vscode-containers`) — 🔴 пока не используется

**Docker сознательно НЕ ставим** (решение Ярослава от 07.08.2026). Причина —
цена/польза, а не принцип:

- Docker Desktop + WSL2 (у нас не установлен) = **10–25 ГБ, растущих со временем**;
  WSL-диск `.vhdx` сам не сжимается. Системный диск — Crucial BX500 на 240 ГБ, который
  недавно был забит на 97% и из-за этого тормозил всю машину (см. §7.2).
- Реальная польза для нас **одна**: воспроизвести VPS локально (Caddy + uvicorn) и
  наконец протестировать `server/Caddyfile` — единственный файл продукта БЕЗ тестов
  (это уже стоило прод-бага: CSP резал картинки Klipy, см. шапку 3.5.5).
- Десктоп (PySide6/WebView2) и сборка Nuitka не контейнеризуются в принципе.

**Когда вернуться:** если понадобится проверять Caddyfile/CSP до деплоя или тестировать
на настоящем PostgreSQL. ⚠️ Довод «прод — PostgreSQL» ОШИБОЧЕН: на бою SQLite под
SQLCipher (§8.0), то есть разрыва dev/prod по СУБД сейчас нет, и польза от Docker
здесь меньше, чем считалось.
Ставить **на D:** — и приложение, и хранилище образов.
Только PostgreSQL — нативный установщик для Windows (~300 МБ) дешевле в 20+ раз.

### Debugger for Firefox (`firefox-devtools.vscode-firefox-debug`) — 🔴 не наш профиль

Говорю прямо, а не придумываю применение: **Firefox не целевой браузер продукта.**
Десктоп рисует WebView2 (движок Edge/Chromium), сайт и мобилка — Chromium. Отлаживать
в Firefox то, что у пользователей работает в Chromium, — проверять не тот код.
Плюс **на машине разработки браузер запускать нельзя** (§8.2: dev-browser трижды
вешал компьютер, один раз Chrome раздулся до 10 ГБ).

**Единственный сценарий, когда пригодится:** отдельная задача «проверить сайт в
Firefox» (студенты им пользуются). Тогда запускает **человек**, не агент, и присылает
скриншоты — как и договорено в §8.2.
