## 1. Что делаем

Активность — совместное действие участников беседы: доска, викторина, опрос, срез
понимания, таймер. Запускает преподаватель (или тот, кому владелец беседы выдал право),
участвуют все, кто в беседе.

**Область:** только общие беседы (`Conversation.kind in ("group", "channel")`). Личные
чаты, «Избранное» и чат модерации активностей не имеют — там либо один собеседник, либо
один человек, либо служебный поток.

**Одна активность на беседу одновременно.** Вторая параллельная — это гонка за экран
студента и два источника правды «что сейчас идёт». Попытка запустить вторую — `409` с
именем текущей и её хостом.

## 2. Ключевые решения и почему именно так

Сведено в одно место, чтобы при дополнении документа не переспорить самих себя.

| Решение | Почему |
|---|---|
| Активности живут в **беседе**, не в учебной группе | у `Conversation` нет связи с `Group` — чат-группа это просто список людей |
| Эндпоинты под **`/web/messenger/activities`** | этот префикс уже в `_PROXY_PREFIXES` (`desktop/local_api.py`) — внутри программы всё работает без единой правки десктопа |
| Ход **синхронной** активности — в памяти процесса | иначе тридцать одновременных ответов = тридцать транзакций в SQLite с блокировкой записи в худший момент |
| Обычная викторина — **асинхронная**, один запрос на участника | 30 запросов вместо 600 на группу в 30 человек |
| Проверка ответов — **на сервере**, не на клиенте | локальная проверка требует прислать клиенту ключ; студент читает его в инструментах разработчика |
| Доска хранится **штрихами**, не картинкой | файлового хранилища в проекте нет вообще; и продолжить рисование можно только штрихами |
| Автор отзыва хранится, но **не виден преподавателю никогда** | иначе жалоба админу ни к чему не ведёт |
| Оценка **не сходит** в учебный журнал | беседа не связана с учебной группой; вместо этого — журнал беседы (§9) |

⚠️ **Активности закрепляют нас на ОДНОМ процессе uvicorn.** Реестр сокетов (`_WSManager`)
уже живёт в памяти по той же причине; состояние активности встанет рядом. Второй воркер
(`--workers 2`) сломает оба — понадобится Redis или PostgreSQL с LISTEN/NOTIFY. Принимаем
осознанно; при реализации записать это в CLAUDE.md.

## 3. Права

Новое право **`activities`** в `_ALL_PERMISSIONS` (`routers/messenger.py`), рядом с
`kick` / `manage_roles` / `cmd_mute` / `cmd_clear`.

```text
может_запустить(user, conv) =
      conv.kind in ("group", "channel")
  AND ( "activities" in _permissions_for(db, participant)      # владелец и его роли
        OR user.role in ("teacher", "admin") )                 # системная роль — сверх ролей беседы
  AND user не в глобальном мьюте (MutedUser)
  AND participant.silenced == False
```

- Владелец беседы получает право как часть полного набора (`owner` — все права) и может
  выдать его своим кастомным ролям через уже существующий редактор ролей.
- **Системная роль `teacher`/`admin` даёт право автоматически**, минуя роли беседы:
  преподаватель ведёт занятие, а не администрирует чат.
- Участвовать может каждый участник беседы; запрет писать (`silenced`) не мешает отвечать
  на викторину — это не сообщение.

⚠️ **`test_conversation_roles.py:31` сверяет набор прав ТОЧНЫМ множеством** и покраснеет.
Падение законное, но проверку заодно перевести на проверку свойства — та же грабля, что
со сторожем прокси-префиксов: сторож, краснеющий от каждой честной правки, обесценивается.

## 5. Данные

Все таблицы — **онлайн-only, НЕ в `SYNC_MODELS`** (как весь мессенджер): офлайновому
десктопу активности не нужны, а внутрь программы они приезжают прокси-префиксом.

### 5.1. `Activity` — что и где идёт

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | String PK | `act:{uuid4().hex}` |
| `conversation_id` | String, index | беседа |
| `kind` | String | `board` / `quiz` / `contest` / `poll` / `pulse` / `timer` |
| `host_id` | String, index | кто запустил |
| `title` | String | что показывать в карточке |
| `params` | JSON | параметры категории (вид листа, длительность, id викторины…) |
| `status` | String, index | `running` / `finished` |
| `started_at` / `finished_at` | String | ISO, ставит сервер |
| `message_id` | Integer | карточка в ленте (для гашения при завершении) |

⚠️ `id` — **uuid, а не составной ключ с именем беседы или группы**. В этом проекте имя
группы в пути URL уже стоило поломки всех отчётов на группах со слэшем («К74/1» →
`%2F` → Starlette раскодирует ДО роутинга → путь распадается). Всё, что идёт в путь, —
только uuid.

### 5.2. `QuizSet` / `QuizQuestion` / `QuizOption`

`QuizSet`: `id` (`quiz:{uuid}`), `author_id`, `title`, `description`, `tags` (JSON-список),
`visibility` (`private` / `college` / `stock`), `parent_id` (для ветвей копий),
`created_at`, `updated_at`, `deleted`.

`QuizQuestion`: `id`, `quiz_id` (index), `order_no`, `type`
(`single` / `multi` / `order` / `match`), `text`, `points`.

`QuizOption`: `id`, `question_id` (index), `order_no`, `text`, `is_correct` (для
`single`/`multi`), `match_key` (для `match`), `correct_position` (для `order`).

🔑 **`is_correct` / `correct_position` / `match_key` не покидают сервер для студента** —
см. §6, эндпоинт выдачи вопросов имеет два режима.

### 5.3. `ActivityResult` — итог участника

`id`, `activity_id` (index), `user_id` (index), `score`, `correct_count`, `total_count`,
`answers` (JSON — что именно ответил, для разбора), `finished_at`, `duration_ms`.

Уникальность по паре `(activity_id, user_id)`: **повторная отправка не создаёт вторую
строку**, а заменяет — иначе дрогнувшая сеть сдвоила бы результат.

### 5.4. `ActivityFeedback` — срез понимания

`id`, `activity_id` (index), `user_id` (index, **скрыт от преподавателя**),
`score_1_10`, `reason_code`, `custom_text`, `created_at`.

### 5.5. `BoardArtifact` — сохранённая доска

`id` (`board:{uuid}`), `conversation_id` (index), `activity_id`, `author_id`, `sheet`
(`blank` / `grid` / `lined`), `strokes` (JSON), `title`, `created_at`.

### 5.6. Правки существующего

- **`Message.kind` получает значения `activity` и `board`.** Колонка уже есть — **миграция
  НЕ нужна**, добавляются только значения. Ссылка на объект кладётся в `body` (`act:…` /
  `board:…`), а в ответ сервер подмешивает готовый объект — ровно так уже устроены
  карточки отчётов куратора (`msg.kind === 'report'` + `msg.report`).
- **`MessageReport.target_kind`** — новая колонка (`message` по умолчанию |
  `activity_feedback`). ⚠️ **Требует идемпотентного ALTER в `db.py`**: `create_all`
  дописывает только целые таблицы, но не колонки в существующие. Это правило спасало прод
  четырежды. Регрессия — в `test_db_migrations.py`, по образцу соседних.

## 6. HTTP API

Все под `/web/messenger/activities` (значит, в программе работают через прокси без правок).

### Общее

| Метод | Путь | Кто | Что |
|---|---|---|---|
| POST | `/start` | право `activities` | запустить: `{conversation_id, kind, params}` → `Activity` + карточка в ленте. `409`, если уже идёт |
| POST | `/{id}/finish` | хост, админ | завершить; для доски — `{save: true/false}` |
| GET | `/current?conversation_id=` | участник | что идёт сейчас (для входа в уже начатую) |
| GET | `/{id}` | участник | состояние активности |
| GET | `/journal?conversation_id=` | участник | журнал беседы (§9) |

### Викторины (библиотека и конструктор)

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/quizzes?q=&tag=&scope=` | teacher/admin | поиск: `scope` = `mine`/`college`/`stock` |
| GET | `/quizzes/{id}` | teacher/admin | **с правильными ответами** |
| GET | `/quizzes/{id}/similar` | teacher/admin | похожие по тегам |
| POST | `/quizzes` | teacher/admin | создать |
| PUT | `/quizzes/{id}` | автор | править **только свою** |
| POST | `/quizzes/{id}/copy` | teacher/admin | копия себе, `parent_id` = оригинал |
| DELETE | `/quizzes/{id}` | автор, админ | мягкое удаление |

### Прохождение

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/{id}/questions` | участник | вопросы **БЕЗ правильных ответов**, порядок вариантов перемешан |
| POST | `/{id}/submit` | участник | `{answers:[…]}` — один раз, все ответы; сервер проверяет и возвращает результат |
| POST | `/{id}/answer` | участник | **только соревнование**: ответ на текущий вопрос |
| POST | `/{id}/next` | хост | **только соревнование**: следующий вопрос |
| GET | `/{id}/results` | хост; участник — своё | таблица: баллы, верные, места |

## 7. События WebSocket

Своего канала нет: используем `ws_manager.emit_users(_participant_ids(conv_id), data)` —
тот же примитив, что рассылает `changed` в мессенджере. Приём от участников идёт по HTTP:
ответ студента — единичное действие, и REST даёт готовую проверку прав, аудит и понятные
коды ошибок. Сокет только вниз.

```jsonc
{"type": "activity.started",  "activity_id": "act:…", "conversation_id": "conv:…",
 "kind": "quiz", "host_id": "teach:…", "title": "…"}

{"type": "activity.state",    "activity_id": "act:…", "seq": 17, "payload": { /* по категории */ }}

{"type": "activity.finished", "activity_id": "act:…", "summary": { /* итог */ }}
```

- **`seq` монотонный.** Кадр с меньшим `seq`, пришедший позже, клиент отбрасывает. Приём,
  уже дважды спасавший этот проект от гонок (расписание, категории), — сверяться по
  монотонному счётчику, а не по значению поля, которое сам же запрос и меняет.
- **Штрихи доски шлются пачками раз в ~150 мс**, не на каждое движение пальца: иначе один
  рисующий даст сотни запросов в секунду.
- **Таймер не тикает по сокету.** Сервер один раз присылает время окончания, отсчёт
  считает клиент. Тик каждую секунду всем участникам — самая дорогая реализация самой
  дешёвой функции.

## 8. Категории

### 8.1. Общая доска

Виды листа: **пустой / в клетку / в линию** → подтверждение → полный экран.

- Пишет **хост**; любому участнику хост **выдаёт перо** (в том числе жребием по ростеру
  беседы, с памятью, чтобы один не выпадал дважды подряд) — это и есть бывшая категория
  «случайный выбор отвечающего». Перо снимается одним нажатием.
- **«Снимок в чат»** — не завершает активность: на доске много написано, и это не должно
  пропасть.
- **При завершении хост выбирает: сохранить или удалить.** Сохранённая сходит сообщением
  (`kind="board"`) и доступна при создании новой активности — «продолжить доску».

🔑 **Штрихи, а не картинка:**

1. **Файлового хранилища в проекте нет** — картинки живут `data:`-строками в JSON
   (аватарки, `me.py::_sanitize_profile_media`). PNG доски — сотни килобайт base64 в теле
   сообщения: раздутая таблица и лишний трафик при каждой загрузке ленты. Настоящее
   хранилище — отдельная задача с диском (на бою свободно 2.6 ГБ), раздающим маршрутом и
   правкой CSP.
2. **Продолжить можно только штрихи** — поверх растра рисуют заново.
3. Штрихи весят единицы-десятки килобайт и чётки на любом экране.

Снимок и сохранение дают **один артефакт**, в ленте он рисуется тем же компонентом.

### 8.2. Опрос

Вопрос и варианты, без правильных ответов.

- **Распределение видит только создатель.**
- Студенту показываем **«проголосовало N из M»** — число ничего не раскрывает и снимает
  вопрос «дошло ли».
- Голос **не анонимен для сервера** (иначе ни накрутку не поймать, ни ошибочное нажатие не
  исправить). В интерфейсе формулировка честная: «результаты видит только преподаватель».

### 8.3. Срез понимания (1–10)

Хост жмёт кнопку → у всех появляется плашка → через заданное время (по умолчанию 60 с,
хост может закрыть раньше) она исчезает → у хоста сводка.

Плашка: шкала **1–10** и «что именно непонятно» — готовые пункты, «в целом понятно, но X»,
**«другое»** со своим текстом.

🔑 **Преподаватель не видит авторов НИКОГДА — ни до жалобы, ни после.** У отзыва только
кнопка «ОК» и маленький значок жалобы: нажал → выбрал категорию → жалоба ушла **админу**
в ту же вкладку «Жалобы», где разбирается всё остальное. **Админ видит и автора, и текст**
и дальше решает сам — передать куратору или нет.

Отсюда единственное следствие: **сервер обязан хранить автора отзыва**, иначе жалоба
никуда не ведёт. Скрывает автора интерфейс преподавателя, а не база. Поэтому студенту
пишем **«преподаватель не увидит, кто это написал»**, а не «анонимно»: первое правда,
второе нет, и первая же разобранная жалоба это вскроет.

### 8.4. Викторина (асинхронная)

Прохождение: сервер отдаёт вопросы **без ключа** → студент проходит **в своём темпе,
локально** → в конце **один POST** со всеми ответами → сервер проверяет и возвращает
результат.

Нагрузка: **один запрос на участника** вместо одного на вопрос (30 вместо 600 на группу в
30 человек). Сеть моргнула посреди прохождения — ничего не потеряно.

🔑 **Почему не проверять на клиенте:** для локальной проверки нужен ключ, а любой студент
откроет инструменты разработчика и прочитает его до начала. Один запрос в конце почти так
же дёшев, но ключ остаётся на сервере.

**Типы заданий:** `single` (один ответ), `multi` (несколько), `order` (расставить по
порядку), `match` (сопоставить термин и определение).

**Библиотека, поиск, теги.** Теги вида `математика`, `дроби`, `логарифмы`; поиск по
названию и тегу; из открытой викторины — «похожие по тегам». Теги свободные, но при вводе
показываем уже существующие и нормализуем регистр и пробелы: закрытый справочник кто-то
один раз заполнит неудачно, а полностью свободные разredутся на «матем» / «математика» /
«Математика».

⚠️ Поиск по подстроке делаем **в Python**, а не через `LIKE`: SQLite без ICU не умеет
регистронезависимый `LIKE` для кириллицы. Этот приём в проекте уже применён дважды
(каталог мессенджера, поиск по чату) — третьей копии правила не заводим, берём готовую.

**Стартовые викторины** — немного, чисто для знакомства с механикой, чтобы первый
открывший не увидел пустой экран. Наполнение по предметам — работа преподавателей.

**Копии и ветви.** Чужую нельзя править — её **копируют себе**, `parent_id` даёт цепочку
`оригинал → копия 1 → копия 2`. Цепочка показывается, **только если в ней больше одного
автора**: ветки внутри одного преподавателя сворачиваются — это его кухня, а не история
заимствований.

### 8.5. Соревнование (синхронное)

То же, но:

- **только `single` и `multi`**: в `order` и `match` спорна цена частично верного ответа,
  а в соревновании нужен бесспорный балл;
- вопрос показывается **по команде хоста всем разом**, таблица обновляется живьём,
  скорость ответа влияет на баллы;
- в конце — **награждение за 1, 2 и 3 место** и таблица: баллы и число верных;
- порядок вариантов перемешивается у каждого — дешёвая защита от «подсмотрел у соседа».

Синхронность здесь оправдана: это и есть смысл категории. Всплеск на 5–10 минут, не фон.

### 8.6. Тайм-бокс

Хост задаёт длительность, отсчёт у всех разом, в конце общий сигнал; хост может
остановить и продлить. Ничего не хранится.

## 9. Журнал активностей беседы

Отдельная вкладка беседы: **дата · категория · тип задания · участники · результат**.

Замена тому, чего сделать нельзя: автоматически выставить оценку в учебный журнал не
получится — беседа не связана с учебной группой. Собственный журнал беседы честен: он про
то, что происходило именно здесь.

- **Хост и обладатели права `activities`** видят таблицу целиком.
- **Участник** — только свои строки.
- Выгрузка таблицей — да. Запись в учебный журнал — отдельный разговор, если понадобится.

## 10. Клиент

**Запуск — команда `/активность`** (по образцу `/отчет`, `/mute`, `/clear`): разбирается в
`send_message` ДО сохранения, литералом в ленте не оседает. Команда русская и не
переводится — её проверяет сервер, от языка интерфейса она не зависит.

**Оверлей выбора** категории → **единая модалка подтверждения** «Вы выбрали X,
подтвердить?» с двумя кнопками (один компонент на все категории) → **полный экран**.

**Режимы окна.** В правом верхнем углу — «выйти» и «свернуть». Свёрнутая активность
превращается в **плавающее окошко**, которое следует за человеком по вкладкам (как
свёрнутая трансляция в Discord) и перетаскивается по углам. Живёт в `AppShell` поверх
`RouterView`, состояние — в Pinia, поэтому переживает переходы между разделами.

⚠️ `AppShell` — то самое место, где `mode="out-in"` у `<transition>` однажды намертво
вешал переходы между страницами. Плавающее окно вешаем **рядом** с `RouterView`, а не
внутрь него, и в анимацию переходов не вмешиваемся.

**Карточка в ленте.** Как только активность создана, от лица хоста появляется
сообщение-кнопка **«Активность»** с таймером от начала; нажатие открывает её. Хост
завершил — карточка остаётся в истории, но **не кликабельна**. Механизм готовый: так уже
устроен отчёт куратора (`msg.kind === 'report'` → кнопка → оверлей).

**Мобильный.** Всё в вебе — на телефоны едет по воздуху (OTA), перезалив APK в RuStore не
нужен. Доска на телефоне — режим «смотреть», рисование с пальца включаем, но кнопкой.

**i18n.** Весь видимый текст сразу в ru/en/zh — `i18n.test.mjs` держит парность намертво.
Пространство имён `activity.*`, `quiz.*`, `poll.*`, `pulse.*`, `board.*`.

## 11. Тесты

Серверные (`server/tests/test_activities.py` и далее по категориям):

- запуск без права — `403`; преподаватель без роли в беседе — `200`;
- запуск в личном чате / «Избранном» — `403`;
- вторая активность в той же беседе — `409`;
- **вопросы студенту приходят без `is_correct`/`correct_position`/`match_key`** — главный
  тест безопасности категории;
- повторный `submit` заменяет результат, а не создаёт второй;
- `poll-results` не-создателю — `403`;
- **сводка отзывов хосту не содержит `user_id` ни в одном поле**;
- жалоба на отзыв создаёт тикет, в котором админ видит автора;
- чужую викторину нельзя `PUT`, но можно `copy`; у копии проставлен `parent_id`;
- ветвь из одного автора не отдаётся клиенту (сворачивание — на сервере, не в UI);
- миграция `MessageReport.target_kind` на старой схеме (`test_db_migrations.py`).

Веб (`web/tests/`): формат событий, отбрасывание кадра с меньшим `seq`, i18n-парность.

⚠️ **У каждой новой проверки убедиться, что она краснеет при откате правки.** Зелёный
тест, который зелен всегда, — это не тест; в этом проекте такое уже находили.

## 12. Этапы

Каждый этап заканчивается зелёными тестами и выкладывается отдельно.
**Все восемь пройдены** (16.08.2026, Release 3.7.4) — плюс переработка вида по образцам
заказчика, отмеченная в §15.

1. **Каркас.** Право `activities`, `Activity`, `/start` + `/finish` + `/current`, команда
   `/активность`, оверлей выбора, подтверждение, карточка-кнопка с таймером, полный и
   свёрнутый режимы, события по WS. Без единой категории — но полный цикл.
2. **Тайм-бокс.** Первая категория именно потому, что простейшая: проверяет каркас
   целиком, а ломаться в ней нечему.
3. **Опрос.** Приём ответов, результат только создателю, счётчик проголосовавших.
4. **Срез понимания.** Свободный текст, обезличенный показ, жалоба админу,
   `MessageReport.target_kind` + миграция.
5. **Викторина.** Библиотека, теги и поиск, конструктор, четыре типа заданий, асинхронное
   прохождение с проверкой одним запросом, копии и ветви.
6. **Соревнование.** Надстройка: синхронный режим, баллы, места, таблица.
7. **Журнал беседы.** Витрина поверх уже накопленных результатов.
8. **Доска.** Последняя: самая дорогая по трафику и единственная со своим артефактом.

## 15. Что изменилось против первоначального замысла (16.08.2026)

Разбор по живому отзыву. Записано здесь, а не только в CLAUDE.md, чтобы следующий
читатель не сверялся с уже неверным планом.

- **Опрос — не оверлей, а СООБЩЕНИЕ в ленте** с кнопками (как в Telegram), плюс срок
  окончания и переключатель «видно, кто как проголосовал». План предполагал такой же
  оверлей, как у остальных категорий: на практике ради вопроса в один клик открывать
  полноэкранное окно и потом его закрывать — три действия вместо одного, и до конца
  доходит меньше людей, чем спросили.
- **Таймер и срез понимания не оставляют следа в ленте вовсе** (`_LEAVES_TRACE_IN_FEED`).
  Они живут минуты и всплывают у всех сами; на паре их запускают по нескольку раз, и
  отметка о каждом превращала переписку в мусор.
- **Активность в ленте — разделитель по центру**, а не пузырь-сообщение: пузырь от лица
  преподавателя читался как реплика, которую можно процитировать, переслать или удалить.
- **Таймер живёт полоской под названием беседы**, а не только внутри окна: на таймер
  поглядывают, продолжая работать, а полноэкранное окно закрывает как раз то, над чем
  работают. Кнопки паузы и завершения — только у ведущего.
- **Ведущий видит МОНИТОРИНГ, а не задание**: он тест не проходит, ему нужно знать, кто
  закончил, а кого ещё ждать.
- **Табло соревнования видят все**, а не только ведущий: места всё равно объявляются
  вслух, а скрытые баллы убирают из игры единственное, что тянет к следующему вопросу.
- **Сопоставление — выпадающий список** из перемешанных половин, а не поле ввода: с полем
  попасть в ответ можно было только дословным совпадением, то есть задание проверяло
  грамотность, а не знание.
- **Доска: объекты вместо одних лишь линий** (прямоугольник, овал, стрелка, надпись),
  панель внизу с цифрами-горячими клавишами, ластик по объекту, «Вызвать к доске» со
  списком участников. Отсутствие типа у объекта = линия от руки — старые сохранённые
  доски обязаны открываться.
- **Штрихи уезжают кусками раз в 150 мс**, а не по отрыву пера: иначе «реальное время»
  им не было — на длинной линии остальные секундами смотрели в пустую доску.
- **Ограничение времени на тест** задаётся в конструкторе и считается от ОТКРЫТИЯ теста,
  а не от старта активности: зашедший в беседу через десять минут не должен терять время.
