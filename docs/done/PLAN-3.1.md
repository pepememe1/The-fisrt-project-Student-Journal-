1. **«ДЗ с нумерацией с №1» — это не разработка, а добавление строки в три списка типов.**

2. **Родитель не «протечёт» в поиск случайно** — каталог собеседников работает по белому
   списку ролей, а не по чёрному. Это редкий случай, когда исходная архитектура уже
   защищает новую фичу.
3. **Мессенджер-задачи 4 и 5 закрывать нечем — они закрыты.** Осталось три AI-пункта и
   два системных канала.

## 1. ДЗ как тип занятия

**Объём: полдня.**

- Добавить `'ДЗ'` в списки типов: `web/.../TeacherJournal.vue::LESSON_TYPES`,
  десктопный диалог создания занятия (`ui/teacher_dashboard.py::_add_lesson`), голосовые
  команды (`vector/voice_command.py` — «создай ДЗ по …»).
- Заголовок колонки — «ДЗ №N / дата / текст задания» (ветка рядом с `Лекция`/`Экзамен` в
  `_update_table` и в `TeacherJournal.vue`).
- **Часы не начисляются** — ДЗ не лекция и не практика (см. §2).

**Открытый вопрос — влияет ли ДЗ на средний балл** (см. §7, вопрос B). От ответа зависит
`grading.py`: либо ДЗ попадает в общий пул оценок наравне с практикой, либо получает
собственный вес в конфиге, либо не считается вовсе. Формулу дублировать нельзя — правка
только в `grading.py` (инвариант §8), а веса берутся из конфига, не хардкодятся.

## 2. Учебные часы: X/Y до конца обучения

**Объём: 2–3 дня** (главная стоимость — десктоп, потому что журнал там нативный).

### Модель

Новая синкуемая таблица:

```python
class SubjectHours(Base):
    """Плановые часы предмета для группы на семестр. Задаёт админ, показывается
    преподавателю и студенту как «пройдено X из Y»."""
    __tablename__ = "subject_hours"
    id = Column(String, primary_key=True)   # hours:{group}|{subject}|{year}|{semester}
    group_name = Column(String, index=True, default="")
    subject = Column(String, index=True, default="")
    year = Column(String, index=True, default="")
    semester = Column(Integer, index=True, default=0)
    hours_total = Column(Integer, default=0)
    updated_at = Column(String, default="", index=True)
    deleted = Column(Boolean, default=False)
```

**Входит в `SYNC_MODELS`.** Иначе на десктопе (журнал нативный, работает офлайн) счётчик
часов будет пустым — а именно там преподаватель ведёт занятия. Id — детерминированная
строка, как у `schedule_overrides`: автоинкремент столкнулся бы между ПК.

⚠️ Это первая новая синкуемая сущность за долгое время. Урок из `muted_users` работает и в
обратную сторону: **нельзя** класть часы полем в `groups` — `_row_to_dict` отдал бы
десктопу неизвестную колонку. Отдельная таблица + миграция на обеих сторонах — правильный
путь, но десктопную часть (`data/core.py`, схема SQLite, `sync_engine`) надо сделать
**в том же заходе**, иначе синк начнёт возить таблицу, которую клиент не понимает.

### Пройденные часы

Считаются из `lessons`, а не хранятся — хранимый счётчик разъехался бы при удалении
занятия. Учитываются только `type ∈ {Лекция, Практика}`.

⚠️ Тут есть тонкость, которую надо решить до кода (вопрос A в §7): лекция в базе лежит
**двумя строками** (`hour=1` и `hour=2` — это одна пара, разбитая по академическим часам),
а практика — **одной**. Наивный подсчёт «строка = час» даст лекции 2 часа, а практике 1 —
то есть занизит практику вдвое.

### UI

- **Админ:** `AdminGroups.vue` → выбрать группу → список её предметов, у каждого поле
  «часов на семестр» → «Сохранить». Эндпоинты `GET/POST /web/admin/group-hours`.
- **Преподаватель:** над таблицей журнала — «Пройдено 24 из 72 ч» для выбранной пары
  группа+предмет. Данные уже загружаются вместе с журналом — отдельного запроса не нужно.
- **Студент:** в `StudentJournal.vue` при выборе предмета — та же строка.
- **Десктоп:** те же две строки в `teacher_dashboard` и `dashboards.py` (журнал студента).

## 3. Домашнее задание → уведомление студенту

**Объём: 1 день.**

- При создании занятия `type='ДЗ'` поле «Тема» переименовывается в «Домашнее задание».
  Отдельного столбца в БД не нужно — `Lesson.topic` уже несёт текст и уезжает синком.
- Сервер создаёт `NotifyEvent(kind='homework')` **каждому студенту группы**:
  `title='ДЗ по «Базы данных»'`, `body='создать базу данных'`. Текст рендерится на сервере
  в момент создания (как у остальных событий) — история не должна переписываться задним
  числом при правке шаблона.
- Пуш через `rustore_push`: в тело пуша идёт только «Новое домашнее задание» + id события.
  Сам текст задания приложение забирает по защищённому каналу — правило `NotifyEvent`
  (третья сторона не должна видеть содержимое).
- **Фильтр во вкладке уведомлений:** «Все / ДЗ / Система» — `NotificationsInbox.vue` и
  `ui/notifications_view.py`. Фильтрация по `kind` на клиенте: событий у студента десятки,
  серверный параметр тут лишний.
- Правка/удаление занятия-ДЗ: уведомление **не** пересоздаётся (иначе правка опечатки
  разошлёт повторный пуш всей группе). При удалении — событие гасится.

## 4. Роль родителя

**Объём: 5–7 дней. Самая крупная и самая рискованная часть.**

### Связь родитель → студент

Поле `User.linked_students` (JSON-список `users.id`) у пользователя с `role='parent'`.

Почему полем, а не таблицей связи: `users` уже в `SYNC_MODELS`, поле уедет на десктоп
обычным pull'ом — ровно так устроен `curated_groups`, паттерн проверен в бою. Обратный
поиск («кто родители этого студента») — фильтр в Python, как в `directory`: датасет
колледжа умещается в память, а SQLite без ICU всё равно плохо ищет по кириллице.

Привязка — только по **неизменяемому `users.id`**, никогда по ФИО (инвариант §10 и урок
миграции оценок: фамилия меняется при замужестве, id — нет).

### Кто привязывает

- **Админ** — на карточке студента, `POST /web/admin/students/{id}/parents`.
- **Куратор** — то же, но `_require_curated(user, student.group_name)`: чужую группу
  трогать нельзя. Аудируется (`audit.py`) — привязка даёт доступ к ПДн ребёнка.

### Кабинет родителя — 5 вкладок

| Вкладка | Как делаем |
|---|---|
| Журнал | `/web/parent/journal?student_id=…` — переиспользует `webdata.student_records` + `grading.average`. **Только чтение.** Если детей несколько — переключатель сверху |
| ИИ Помощник | `/web/parent/vector/ask` — роль-скоуп «только мой ребёнок». В `vector_nlu` роль `parent` ведёт себя как `student`, но подставляется `student_id` ребёнка |
| Сообщения | см. ниже |
| Настройки, Профиль | существующие страницы, доступны как есть |

Никаких дашбордов, статистики по группе, расписания преподавателей — навигация задаётся
`NAV.parent` в `web/src/config/nav.js`, доступ — guard'ом в роутере **и** проверкой роли на
сервере (инвариант §6: UI-скрытие само по себе не защита).

### Мессенджер для родителя

Правила доступа, которые надо реализовать явно:

1. **Родитель невидим** в каталоге для студентов и преподавателей — уже так по построению
   (`directory` пускает только `student|teacher`). Добавляем вкладку «Родители» и
   открываем её **только** админу и куратору, причём куратору — лишь родители его групп.
2. **Личный чат родитель↔родитель** — только при общей группе (у детей). Проверка при
   создании direct-чата, а не только в поиске: иначе id собеседника можно подставить руками.
3. **Родитель↔куратор** — разрешён (это и есть заявленный «доступ к группе куратором»).
4. **Родитель↔студент и родитель↔преподаватель (не куратор)** — запрещены.
5. **Беседу группы создаёт только куратор** — `_guard_can_create` уже пускает лишь
   `teacher|admin`, роль `parent` туда не добавляем. Ничего делать не нужно.

### Десктоп

**Рекомендация: кабинет родителя целиком через `QWebEngineView`** (Фаза 0 «один UI»,
внутренние заметки §11) — как уже сделано с мессенджером и модерацией.

Обоснование: родителю offline-first не нужен — он смотрит оценки из дома, онлайн, изредка.
Нативный Qt-порт журнала, Вектора и мессенджера ради этой роли — недели работы ради
сценария, который web-view закрывает за час. Инвариант offline-first не нарушается: он
защищает *преподавателя в аудитории без сети*, а не родителя на диване.

### ⚠️ Правовая сторона (152-ФЗ)

Родитель получает доступ к ПДн другого человека — своего ребёнка. Для несовершеннолетнего
это законно (законный представитель), но связь должна быть **документально обоснована**:
привязку делает сотрудник колледжа, действие аудируется, и есть кому ответить на вопрос
«на каком основании». Для **совершеннолетнего** студента (а в колледже это 3–4 курс)
доступ родителя без согласия самого студента — уже нарушение. Это вопрос C в §7.

## 5. Мессенджер — остаток

### §12 Системные каналы (осталось 2 из 4)

- **«Замены»** — источник есть: `ScheduleOverride` уже фиксирует правки расписания, а
  событие `schedule_changed` уже рассылается. Канал = лента этих же событий по группе.
  Объём: полдня.
- **«Практика»** — источника данных нет. Это не автоматический канал, а обычный канал,
  который ведёт руками учебная часть. Предлагаю не выдумывать автоматику, а завести его
  как системный канал с правом записи у админа/куратора. Объём: пара часов.

### §17 AI-поиск по смыслу — ✅ СДЕЛАНО

Полноценный семантический поиск (эмбеддинги + векторный индекс) на **одноядерном VPS с
960 МБ RAM** не поедет, а отправлять чужую переписку в облако ради поиска нельзя. Поэтому
сделано наоборот: модель получает **только сам запрос** и придумывает к нему словоформы и
синонимы, а сопоставление с сообщениями идёт у нас обычным вхождением подстроки. Переписка
модели не показывается вообще — это не компромисс, а лучший вариант из доступных.

`GET /chats/{id}/messages/ai-search` + `messenger_ai.expand_query/match_score`. Прямое
совпадение с исходным запросом весит больше синонима. Модель недоступна → результат равен
обычному поиску, поле `expanded` пустое. В интерфейсе расширения показываются строкой
«Ищем также: …» — иначе непонятно, почему нашлось сообщение без искомого слова.

### §18 AI-сводка переписки — ✅ СДЕЛАНО

`GET /chats/{id}/summary`, запуск только кнопкой в шапке чата. ФИО маскируются до отправки
(`messenger_ai.mask_names`). Кэш в памяти по ключу **(беседа, id последнего сообщения, его
метка времени)** — метка добавлена не для красоты: id автоинкрементные, и после
восстановления БД из бэкапа они выдаются заново, а кэш процесса это переживёт и отдал бы
сводку уже несуществующего разговора. Модель недоступна → пустая сводка + причина, а не
выдуманный пересказ.

### §19 AI-напоминания — ✅ СДЕЛАНО

Разбор даты **детерминированный**, без LLM (`reminder_parse.py`) — по той же причине, что
и голосовая запись оценок: модель ошибается молча, а напоминание, съехавшее на день, хуже
ненайденного, потому что на него уже положились.

Хранилище — таблица `Reminder` (не в SYNC_MODELS). Текст храним снимком: автор может
отредактировать или удалить сообщение. **Срабатывание событийное** — просроченные
напоминания материализуются в обычные `NotifyEvent` при запросе `GET /me/events`.
Планировщик ради одной фичи означал бы вечный фоновый поток на одноядерном VPS; плата за
событийную схему — напоминание видно с момента, когда человек открыл приложение, но
уведомления он и так читает только там.

## 7. Принятые решения (Ярослав, 26.07.2026)

**A. Занятие = пара = 2 академических часа.**
Считаем по УНИКАЛЬНЫМ парам `(type, number)`, а не по строкам таблицы: лекция №1 лежит
двумя строками (`hour=1`, `hour=2`) и даёт 2 часа, практика №1 лежит одной строкой и тоже
даёт 2. Совпадает с парой в расписании. В базе менять ничего не нужно — это правило
подсчёта, а не новое поле.

**B. ДЗ считается в средний балл наравне с практикой.**
Отдельного веса не заводим. Следствие, которое надо помнить: как только преподаватель
начнёт ставить оценки за ДЗ, средний балл сдвинется — это ожидаемое поведение, а не баг.
Правка — только в `grading.py` (инвариант §8).

**C. Родитель совершеннолетнего — по подтверждению студента.**
Куратор/админ создаёт привязку, она уходит в статус `pending`; студенту приходит запрос в
кабинет. **До подтверждения родитель журнал не видит.** Работает для любого возраста, то
есть возраст в системе хранить и проверять не нужно вовсе — а значит, не нужно и собирать
дату рождения ради этой фичи (меньше ПДн — меньше рисков). Отклонение и отзыв согласия
студентом — тоже в его кабинете, действие аудируется.

**D. Кабинет родителя на десктопе — web-view** (тот же Vue-SPA в `QWebEngineView`, как
мессенджер и модерация). Нативный Qt-порт не делаем.
