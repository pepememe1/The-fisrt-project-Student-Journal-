## 1. Что строим

Внутренний мессенджер колледжа, **интерфейс точь-в-точь как в Telegram**. Сообщения хранятся
**на серверах колледжа** (не end-to-end), администрация может их просматривать для защиты от
вредоносных/недопустимых сообщений.

Три типа чатов:
- **Личные чаты** — 1-на-1 между двумя пользователями.
- **Группы** — много участников, все пишут (роли владелец/админ/участник).
- **Каналы** — один или несколько «писателей» и сколько угодно «читателей»; читатели только
  читают, могут присоединиться, и канал появляется у них в списке чатов.

Ключевые сценарии (из ТЗ):
- **Список чатов**: клик по чату → **справа** переписка, **слева** карточка собеседника
  (портфолио + безопасные данные + онлайн/оффлайн).
- **Поиск по ФИО** сверху: в результатах видны безопасные данные (группа, курс, кафедра
  преподавания и т.п. — ничего, что помогает угнать чужой аккаунт).
- **Каталог пользователей**: вкладки **Преподаватели / Студенты** по отдельности, сортировка
  по алфавиту. Клик по юзеру → слева портфолио, справа окно чата.
- **Действия над сообщением**: тап по сообщению → небольшой оверлей с кнопками (ответить,
  закрепить, копировать, переслать, удалить, выделить, пожаловаться) — см. §6.
- **Жалоба на сообщение** → тикет автоматически улетает администратору, прикреплённый к
  сообщению (без ручного создания тикета) — см. §6.7 и §10.
- **Шестерёнка ⚙** в верхней полоске чата (где ФИО и статус) → **чат с модерацией**: слева
  краткая сводка (что сюда можно писать, контакты модерации), справа сам чат.

## 2. Ключевые архитектурные решения (и почему)

Прежде чем писать код, договариваемся о фундаменте — эти решения меняют всё.

1. **НЕ end-to-end шифрование.** Требование «администрация может просматривать сообщения»
   несовместимо с E2E (в E2E сервер физически не может прочитать текст). Значит: сообщения
   шифруются **на диске** (SQLCipher целиком, как вся боевая БД) и в канале (TLS), но
   сервер/админ их читают. Осознанный компромисс — **обязательно раскрыть в пользовательском
   соглашении и политике ПДн** (см. §3).
2. **Мессенджер — ОТДЕЛЬНАЯ подсистема, НЕ часть sync-движка.** Сообщения append-only, истина
   всегда на сервере, конфликтов LWW нет. Не добавлять в `SYNC_MODELS` — иначе реконсиляция
   «сервер = истина» вычистит локальный кэш чатов. Транспорт — собственные REST/WS-эндпоинты.
3. **Онлайн-природа vs offline-first.** Переписка требует сервера здесь и сейчас — сознательное
   отступление от offline-first (журнал/оценки остаются offline-first, чат — нет). Десктоп в
   оффлайне показывает кэш истории и ставит исходящие в очередь «отправится при связи».
4. **Транспорт поэтапно: сначала polling, потом WebSocket.** WS на боевом VPS (1 ядро) —
   риск: постоянные соединения жрут воркеры. Стартуем на периодическом опросе (просто,
   тестируемо), WS добавляем отдельной фазой. Реальный дом — сервер колледжа с ресурсами.
5. **Presence переиспользуем существующий** (`events.online()`, окно ~90 c) как `last_seen`;
   точный онлайн даст WS-фаза.
6. **Пуши переиспользуем** (`rustore_push.py`, `PushToken`) — как уведомления об оценке.
7. **Удаление — две семантики.** «Удалить у себя» (скрыть только у меня) и «удалить у всех»
   (тумбстоун для всех). Своё сообщение — обе; чужое — только «у себя». Это влияет на модель
   (см. `MessageHidden` + `Message.deleted_at`).
8. **Жалоба = тикет.** Отдельного «ручного» создания тикета нет: жалоба на сообщение сразу
   создаёт тикет модерации со **снимком текста** сообщения (чтобы контекст сохранился, даже
   если сообщение потом удалят).

## 3. Правовая часть (152-ФЗ) — СДЕЛАТЬ ДО КОДА

Переписка — персональные данные и **тайна связи**. Первый пункт работ, не последний.

- **Согласие и раскрытие.** В соглашении/политике ПДн явно: (а) сообщения хранятся на серверах
  колледжа; (б) переписка НЕ end-to-end и **может просматриваться уполномоченными сотрудниками
  (модерацией)** ради безопасности; (в) сроки хранения; (г) как запросить удаление. Согласие —
  до первого входа в мессенджер, факт согласия фиксируем в аудите.
- **Модерация ограничена и подотчётна.** Доступ к чужой переписке — только у роли
  «модератор/админ», **каждый просмотр логируется** в `audit_events` (кто/что/когда).
- **Данные в РФ, шифрование at-rest (SQLCipher), TLS в канале** — распространяем на новые таблицы.
- **Retention/удаление.** Срок хранения (например, N месяцев), механизм «право на забвение»,
  soft-delete + фоновая физическая чистка.
- **Минимизация в каталоге.** В поиске/каталоге — только whitelisted безопасные поля (§9).

> ⚠️ До утверждения юридической части заказчиком серверный код не начинаем.

## 4. Модель данных (сервер, `server/app/models.py`)

Новые таблицы (в SYNC_MODELS **не** добавлять). Все id — строковые, серверные.

### 4.1 `Conversation` — беседа (любого типа)
- `id` (`conv:{uuid4}`), `kind` (`direct` | `group` | `channel` | `moderation`).
- `title`, `about` (для групп/каналов; у direct — нет, имя = собеседник).
- `avatar_ref` (опц., ссылка на аватар; в v1 можно инициалы).
- `owner_id` (создатель; у direct/moderation — null).
- `is_public` (bool; для каналов — виден ли в каталоге/поиске и можно ли вступить свободно).
- `username` / `join_link` (опц.; публичная ссылка для вступления в канал).
- `created_at`.
- **Direct — идемпотентность:** детерминированный ключ пары `direct:{min(uid)}|{max(uid)}`,
  чтобы не плодить дубликаты; ищем по нему перед созданием.

### 4.2 `ConversationParticipant` — участник
- `conversation_id`, `user_id`, `role` (`owner` | `admin` | `writer` | `member` | `reader`),
  `joined_at`, `last_read_at` (непрочитанное), `muted` (без пушей), `pinned` (закреплён ли сам
  чат в списке у этого пользователя). Индекс по `user_id` (список чатов).
- Роли по типам: direct — оба `member`; group — `owner`/`admin`/`member`; channel —
  `owner`/`admin`/`writer` (могут постить) + `reader` (только читают).

### 4.3 `Message` — сообщение
- `id`, `conversation_id`, `sender_id`, `body` (text), `created_at` (**ставит СЕРВЕР**, UTC).
- `edited_at` (редактирование), `deleted_at` (**удалено у всех** — тумбстоун «сообщение удалено»).
- `reply_to_id` (ответ на сообщение) — nullable FK на `Message`.
- Пересылка (снимок источника, т.к. оригинал может исчезнуть): `fwd_from_sender_id`,
  `fwd_from_conv_id`, `fwd_from_created_at`, `fwd_sender_name` (денормализованное имя).
- Закрепление: `pinned` (bool), `pinned_at`, `pinned_by`. (Список закреплённых = выборка по
  `conversation_id, pinned=true`.)
- Индексы: `(conversation_id, created_at)` — история/пагинация; `created_at` — чистка;
  `(conversation_id, pinned)` — закреплённые.

### 4.4 `MessageHidden` — «удалено у себя»
- `message_id`, `user_id` (композитный PK). Наличие строки = сообщение скрыто у этого
  пользователя (ему не отдаём в истории). На других не влияет.

### 4.5 `MessageReport` — жалоба = ТИКЕТ модерации
- `id`, `message_id`, `conversation_id`, `message_snapshot` (текст на момент жалобы — чтобы
  контекст жил, даже если сообщение удалят), `reporter_id`, `reported_user_id` (автор),
  `reason_code` (enum, см. §6.7), `description` (свободный текст), `created_at`,
  `status` (`open` | `in_review` | `resolved` | `dismissed`), `handled_by`, `handled_at`,
  `resolution_note`. Это и есть тикет: создаётся из жалобы, привязан к сообщению.

Портфолио пользователя (левая панель) — представление поверх существующих
`User`/`Group`/`Subject`/`Lesson`, отдельной таблицы не заводим (см. §9).

## 5. Типы чатов: правила и создание

### 5.1 Личный чат (direct)
- Два участника, оба `member`, оба пишут. Создаётся при первом обращении (см. §8
  `POST /chats/direct/{user_id}`), идемпотентно по ключу пары.

### 5.2 Группа (group)
- Создатель → `owner`. Роли: `owner`/`admin` (управляют), `member` (пишет).
- Создание: экран «Новая группа» → название + (опц.) описание/аватар + выбор участников из
  каталога/поиска. `POST /chats/group`.
- Права: писать — все участники (кроме заглушённых/ограниченных owner'ом позже); добавлять/
  удалять участников, менять инфо, закреплять, удалять-у-всех — `owner`/`admin`.
- Выход/удаление: участник может выйти; owner может удалить группу.

### 5.3 Канал (channel)
- «Один или несколько писателей + сколько угодно читателей». Роли: `owner`/`admin`/`writer`
  (постят), `reader` (только читает).
- Создание: экран «Новый канал» → название + описание + приватность (`is_public`) + начальные
  писатели. `POST /chats/channel`.
- **Вступление читателя:** публичный канал виден в каталоге каналов/поиске → «Присоединиться»
  → создаётся `ConversationParticipant(role=reader)` → канал **появляется в списке чатов**
  читателя, он получает новые посты. `POST /chats/{id}/join`.
- Права: постить/редактировать/удалять посты/закреплять — только `writer`/`admin`/`owner`;
  `reader` — read-only (композер скрыт, вместо него «Вы подписаны» / «Покинуть канал»).
- Управление писателями: owner/admin назначают/снимают роль `writer`.
- (v2, не сейчас) обсуждения/комментарии к постам, реакции.

> Единая таблица `Conversation` + `ConversationParticipant.role` покрывает все три типа —
> разница только в наборе ролей и в проверках «кто может постить/управлять».

## 6. Действия над сообщением (контекстный оверлей) — как в Telegram

**Триггер.** Тап по сообщению (мобилка — long-press; десктоп — ПКМ или клик по «⋯» на пузыре)
→ рядом с сообщением всплывает небольшой оверлей со списком действий. Клик вне оверлея — закрыть.
Набор кнопок зависит от прав (своё/чужое сообщение, тип чата, роль) — см. матрицу в §6.8.

### 6.1 Ответить (Reply)
- Ставит сообщение как «цель ответа»: композер показывает цитату (автор + фрагмент), крестик —
  отменить. Отправка → `Message.reply_to_id = target`. В ленте у пузыря сверху рисуется цитата
  оригинала; тап по цитате → прокрутка к оригиналу (подсветить).

### 6.2 Закрепить (Pin)
- `Message.pinned = true` (+ `pinned_at`, `pinned_by`). Сверху чата — **плашка закреплённого**
  (как в Telegram); если закреплённых несколько — переключение между ними, тап → прокрутка к
  сообщению. Открепить — то же действие/кнопка на плашке.
- Права: direct — оба; группа/канал — `admin`/`owner` (в канале ещё `writer`).

### 6.3 Копировать текст (Copy)
- Чисто клиентское: `navigator.clipboard.writeText(body)` (веб), `QGuiApplication.clipboard()`
  (десктоп). Тост «Скопировано».

### 6.4 Переслать (Forward)
- Открывает **пикер чатов** (поиск + список чатов/пользователей) → выбор одного или нескольких
  адресатов → отправка копий: новый `Message` с заполненными `fwd_from_*` (снимок автора/чата/
  времени). В ленте у пересланного — шапка «Переслано от {имя}».
- Работает и для одного сообщения, и для пачки из режима «Выделить» (§6.6).

### 6.5 Удалить (Delete)
- **Своё сообщение** → диалог «Удалить у себя / Удалить у всех / Отмена».
  - *У всех:* `deleted_at = now` (тумбстоун «Сообщение удалено» у всех). В группах/каналах
    `admin`/`owner` тоже может удалить чужое «у всех».
  - *У себя:* строка в `MessageHidden(message_id, user_id)` — исчезает только у меня.
- **Чужое сообщение** → только «Удалить у себя» (`MessageHidden`), у других остаётся.

### 6.6 Выделить (Select)
- Включает **режим множественного выбора**: на сообщениях — чекбоксы, снизу панель действий с
  счётчиком и кнопками **Переслать** / **Удалить** (и «Копировать», если применимо). Тап по
  сообщениям добавляет/снимает выбор; «Отмена» выходит из режима.
- Массовое «Удалить»/«Переслать» — те же правила прав, что и для одиночных.

### 6.7 Пожаловаться (Report) → тикет админу
- Открывает **модалку жалобы**: список причин (radio) + поле «Опишите подробнее» (textarea):
  `reason_code` ∈ { `spam`, `harassment` (оскорбления/травля), `threats` (угрозы/насилие),
  `fraud` (мошенничество), `illegal` (запрещённый контент), `flood`, `other` }. Для `other`
  описание обязательно.
- Отправка → `POST /reports` создаёт **`MessageReport`** (тикет) со снимком текста, автором
  сообщения, причиной и описанием, `status=open`. Тост «Жалоба отправлена, модерация
  проверит». Тикет **сразу привязан к сообщению** и попадает в очередь админа (§10) — **без
  ручного создания тикета**.
- На своё сообщение «Пожаловаться» не показываем.

### 6.8 Матрица прав действий (что показывать в оверлее)

| Действие      | Своё | Чужое | direct | группа           | канал                       |
|---------------|------|-------|--------|------------------|-----------------------------|
| Ответить      | ✓    | ✓     | ✓      | ✓                | ✓ (у writer; reader — нет)  |
| Закрепить     | ✓*   | ✓*    | ✓      | admin/owner      | writer/admin/owner          |
| Копировать    | ✓    | ✓     | ✓      | ✓                | ✓                           |
| Переслать     | ✓    | ✓     | ✓      | ✓                | ✓                           |
| Удалить у себя| ✓    | ✓     | ✓      | ✓                | ✓                           |
| Удалить у всех| ✓    | admin | автор  | автор/admin/owner| автор/admin/owner           |
| Выделить      | ✓    | ✓     | ✓      | ✓                | ✓                           |
| Пожаловаться  | —    | ✓     | ✓      | ✓                | ✓                           |

\* «Закрепить» в direct доступно обоим; в группе/канале — по роли.

## 7. Транспорт и presence

**Фаза 1 (polling):** клиент опрашивает `GET …/messages?after=<id>` (на активном чате раз в
3–5 c, в фоне реже) и `GET …/chats` (счётчики непрочитанного). Онлайн — из `events.online()`.

**Фаза (WebSocket):** `WS /web/messenger/ws` — события `message.new/edited/deleted`,
`message.pinned`, `message.read`, `presence.changed`, `typing`. Реестр соединений в памяти
процесса (на 1 воркере ок; при `--workers N` — общий брокер, напр. Redis pub/sub — уже сервер
колледжа). Нет WS → авто-деградация на polling.

## 8. REST API (`server/app/routers/messenger.py`, префикс `/web/messenger`)

Все — под JWT; роль/членство проверяются всегда; метку времени ставит сервер.

**Чаты:**
- `GET  /chats` — список бесед пользователя (тип, заголовок/собеседник, последнее сообщение,
  непрочитанные, онлайн; закреплённые чаты сверху). 
- `POST /chats/direct/{user_id}` — открыть/создать личный чат (идемпотентно).
- `POST /chats/group` `{title, about?, member_ids[]}` — создать группу.
- `POST /chats/channel` `{title, about?, is_public, writer_ids[]}` — создать канал.
- `POST /chats/{id}/join` / `POST /chats/{id}/leave` — вступить/выйти (каналы/группы).
- `GET  /chats/{id}` — инфо о беседе (участники/роли — по правам).
- `PATCH /chats/{id}` — изменить title/about/аватар (owner/admin).
- `POST /chats/{id}/members` / `DELETE /chats/{id}/members/{uid}` — управление участниками.
- `POST /chats/{id}/members/{uid}/role` — назначить admin/writer и т.п.

**Сообщения:**
- `GET  /chats/{id}/messages?before=<id>&limit=50` — история (курсор вверх; скрытые через
  `MessageHidden` не отдаём; удалённые-у-всех отдаём как тумбстоун).
- `GET  /chats/{id}/messages?after=<id>` — новые (polling).
- `POST /chats/{id}/messages` `{body, reply_to_id?}` — отправить (сервер ставит `created_at`,
  режет длину, анти-спам). Триггерит пуш. В канале — только writer/admin/owner.
- `PATCH /messages/{id}` `{body}` — редактировать своё (ставит `edited_at`).
- `POST /messages/{id}/pin` / `DELETE /messages/{id}/pin` — закрепить/открепить (по правам).
- `POST /messages/forward` `{message_ids[], to_conversation_ids[]}` — переслать.
- `DELETE /messages/{id}?scope=self|all` — удалить у себя (`MessageHidden`) или у всех
  (`deleted_at`; только автор или admin/owner).
- `POST /chats/{id}/read` `{last_message_id}` — отметить прочитанным.

**Жалобы/каталог:**
- `POST /reports` `{message_id, reason_code, description?}` — создать тикет (§6.7).
- `GET  /users?role=student|teacher&q=<фио>&sort=alpha&page=` — каталог/поиск (§9).
- `GET  /users/{id}/profile` — публичный профиль (§9).
- `GET  /channels?q=&page=` — каталог публичных каналов (для вступления).
- `GET  /moderation` — беседа текущего пользователя с модерацией (для ⚙).

**Модерация (админ, `/web/admin/messenger/…`, `require_admin`):**
- `GET  /reports?status=open` — очередь тикетов (с контекстом сообщения); 
  `POST /reports/{id}/resolve` `{status, resolution_note}`.
- `GET  /conversations?...` + `GET /conversations/{id}/messages` — читать любую беседу.
  **Каждый вызов → `audit_events`.**
- (Опц.) скрыть сообщение/заблокировать пользователя в мессенджере.

## 9. Каталог пользователей, поиск и «портфолио»

- **Поиск по ФИО** — серверный, регистронезависимый, префикс+подстрока.
- **Каталог** — вкладки **Преподаватели** и **Студенты** отдельно, алфавит, пагинация.
- **Whitelist безопасных полей** (строго — ничего для входа в чужой аккаунт):
  - Общие: ФИО, роль, онлайн/`last_seen`, инициалы-аватар.
  - Студент: группа, курс/год, специальность.
  - Преподаватель: кафедра/предметы (из `Lesson`/`Subject`).
  - **НИКОГДА:** логин, email, телефон, хэш пароля, device-id, токены, адрес, документы.
- **Портфолио** (левая панель при открытом чате) = представление поверх существующих таблиц.
  Средний балл/оценки студента другим НЕ показываем (его ПДн).

## 10. Модерация и тикеты

- **Тикеты из жалоб.** Жалоба (§6.7) = `MessageReport` со снимком текста → очередь
  `GET /web/admin/messenger/reports?status=open`. Админ видит: сообщение (снимок + ссылку на
  живой контекст беседы), автора, жалобщика, причину, описание. Действия: `in_review` →
  `resolved`/`dismissed` (+ `resolution_note`). Никакого ручного создания тикета — всё из жалобы.
- **Просмотр переписки** — только роль модератора/админа, **с записью в `audit_events`**.
- **Чат с модерацией (⚙).** У каждого пользователя беседа `kind=moderation`. Левая панель
  экрана — статическая сводка (правила + контакты модерации), правая — чат.
- **Retention** и «право на забвение» (§3). Снимок текста в тикете хранится по политике жалоб.
- (v2) Автофильтры (стоп-слова/ссылки) как первый барьер до ручной модерации.

## 11. UI — точь-в-точь Telegram

Каркас (широкий десктоп; на узком/мобиле — стек с навигацией «назад», как мобильный Telegram):

```
┌───────────────┬─────────────────────┬──────────────────────────────┐
│ A. НАВИГАЦИЯ   │ B. ПРОФИЛЬ/ИНФО      │ C. ЧАТ                       │
│ [ поиск ФИО ]  │  аватар, ФИО         │ ┌──────────────────────────┐ │
│ [Чаты|Преп|Студ]│  группа/курс ИЛИ     │ │ ФИО · онлайн/оффлайн  ⚙  │ │ ← верхняя полоска
│ [+ Новый ▾]    │  кафедра/предметы    │ ├──[ 📌 закреплённое ]──────┤ │
│  • чат …       │  портфолио           │ │  ... лента сообщений ... │ │
│  • группа …    │                      │ │   (пузыри как в TG)      │ │
│  • канал …     │                      │ ├──────────────────────────┤ │
└───────────────┴─────────────────────┴──│ [ ввод ] [📎] [ отпр. ]  │─┘
                                          └──────────────────────────┘
```

- **Колонка A (навигация):** поиск по ФИО; вкладки **Чаты / Преподаватели / Студенты**; кнопка
  **«+ Новый»** → меню «Новый чат / Новая группа / Новый канал». «Чаты» — недавние (закреплённые
  сверху). Каталог — алфавит.
- **Колонка B (профиль/портфолио, СЛЕВА от чата):** карточка выбранного собеседника (§9) или
  инфо о группе/канале (участники/подписчики по правам).
- **Колонка C (чат, СПРАВА):**
  - Верхняя полоска: ФИО/название, онлайн/оффлайн (или «N подписчиков»), кнопка **⚙** (чат
    модерации), меню «⋯».
  - **Плашка закреплённого** под полоской (§6.2).
  - Лента: пузыри Telegram-стиля (свои справа, чужие слева; время; галочки прочтения; цитата
    ответа сверху пузыря; шапка «Переслано от …»; тумбстоун «Сообщение удалено»).
  - **Оверлей действий** по тапу на сообщение (§6): ответить/закрепить/копировать/переслать/
    удалить/выделить/пожаловаться — набор по правам (§6.8).
  - **Режим выделения** (§6.6): чекбоксы + нижняя панель (счётчик, Переслать, Удалить, Отмена).
  - Композер: поле ввода (+ превью цитаты при ответе), отправка; в канале для reader — вместо
    композера «Вы подписаны · Покинуть канал».
- **Модалки:** пикер чатов для пересылки (§6.4); модалка жалобы с причинами (§6.7); экраны
  «Новая группа»/«Новый канал» (§5).
- **⚙ → модерация:** тот же трёхколоночный каркас; B = сводка правил+контакты, C = чат модерации.
- **Адаптив:** узкое окно/мобилка — одна колонка за раз (список → профиль/чат → назад).
- Всё на токенах темы `--gb-*` (не хардкодить цвета).

**Веб-компоненты** (`web/src/pages/MessengerPage.vue` + `web/src/components/messenger/`):
`ChatList`, `UserDirectory`, `NewChatMenu`, `CreateGroupDialog`, `CreateChannelDialog`,
`ProfilePanel`, `ChatHeader`, `PinnedBar`, `ChatThread`, `MessageBubble`, `MessageActionsOverlay`,
`SelectionBar`, `ForwardPicker`, `ReportDialog`, `ModerationPanel`. Store
`web/src/stores/messenger.js` (беседы, активный чат, сообщения, режим выбора, цель ответа,
presence, polling/WS). Пункт меню в `nav.js` для всех ролей.

## 13. Десктоп (PySide6)

- Вкладка «Сообщения» в дашбордах, тот же трёхколоночный каркас на Qt (`QSplitter`).
  Оверлей действий над сообщением — `QMenu`/поповер у пузыря.

  GUI-поток (как `VectorSession`). Оффлайн: кэш истории + очередь исходящих.
- Делаем ПОСЛЕ веба (веб — эталон контракта, потом порт на Qt).

## 14. Безопасность и анти-абьюз

- **Роль/членство на каждом эндпоинте**; доступ к беседе — только участники/модерация; постить
  в канал — только writer/admin/owner.
- **Анти-спам/флуд:** rate-limit на отправку (`throttle.py`), лимит длины, лимит новых бесед и
  вступлений в минуту.
- **Экранирование:** сообщения — текст; на клиенте вывод как текст (без `v-html`) → нет XSS.
- **Вложения — в v1 НЕ делаем** (файлы = вектор вредоносного контента: нужен антивирус-скан,
  проверка типов, отдельное хранилище). Отдельная фаза.
- **Аудит** доступа модерации (§3/§10).

## 16. Фазы = порядок сборки (инструкция)

0. **Право + модель данных.** Соглашение/политика ПДн (§3); таблицы+миграции §4; экран согласия.
1. **Ядро API (polling).** `Conversation`/`Participant`/`Message`; direct-чаты; отправка/история/
   read; список чатов. Тесты роль-скоупа.
2. **Веб-UI ядра.** Трёхколоночный Telegram-каркас; список/каталог/поиск; лента+композер; ⚙-модерация.
3. **Действия над сообщением.** reply → pin → copy → delete(self/all) → forward → select → report.
   Оверлей (§6), плашка закреплённого, пикер пересылки, модалка жалобы. Бэкенд-эндпоинты §8.
4. **Жалобы → тикеты + модерация.** `MessageReport`, очередь админа, просмотр бесед с аудитом.
5. **Группы.** Создание, роли, управление участниками, права действий в группе.
6. **Каналы.** Создание, writer/reader, каталог публичных каналов, вступление → в списке чатов.
7. **WebSocket + presence.** Live-сообщения, точный онлайн, «печатает…», read-receipts.
8. **Пуши + бейджи.** RuStore Push + счётчики непрочитанного.
9. **Десктоп.** Порт каркаса и оверлея действий на Qt поверх того же API.
10. **v2 (позже).** Вложения (с антивирусом), реакции/стикеры, комментарии к постам канала,
    поиск внутри переписки, автофильтры модерации.

## 18. Что НЕ делаем в v1 (чтобы не расползлось)

Вложения/файлы/голосовые · реакции/стикеры · комментарии и обсуждения под постами канала ·
редактирование чужих сообщений · звонки · E2E-шифрование (несовместимо с модерацией) ·
интеграция мессенджера в sync-движок. Всё это — потенциальный v2 после рабочей текстовой версии
(личные чаты + группы + каналы + действия над сообщением + жалобы→тикеты).
