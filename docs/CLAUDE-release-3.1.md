## 14. Релиз 3.1 — ДЗ, учебные часы, роль родителя (план — `docs/done/PLAN-3.1.md`)

**ДЗ — обычный тип занятия** (`Lesson.type == "ДЗ"`), «тема» несёт текст задания. Своя
нумерация с №1 работала и раньше (автонумерация считает максимум В ПРЕДЕЛАХ типа). Оценка
за ДЗ идёт в средний балл наравне с практикой (`grading.PRACTICE_TYPES`) и в долги, но НЕ
в пропуски: «Н» на домашней работе значит «не сдал», а не «не был».
При создании ДЗ студенты группы получают `NotifyEvent(kind='homework')` — и с сайта
(`web.teacher_create_lesson`), и с ДЕСКТОПА (`sync.push`, при ПЕРВОМ появлении строки —
иначе полный снимок каждые N циклов слал бы одно и то же ДЗ снова). Текст задания есть в
нашем письме, но НЕ в теле пуша (пуш идёт через RuStore). Во вкладке уведомлений — фильтр
«Все / ДЗ / Система» (веб + десктоп).

**Учебные часы** — таблица `SubjectHours` (**в SYNC_MODELS**: журнал на ПК нативный и
работает офлайн). Задаёт админ: «Группы» → 🕐 → часов на семестр по каждому предмету —
кнопка есть и на сайте (`AdminGroups.vue`), и в десктоп-админке
(⚠️ прежняя нативная кнопка `ui/admin_dashboard.py::_open_group_hours` удалена вместе с Qt —
осталась одна, в SPA; она и раньше шла через тот же REST
`/web/admin/group-hours`, а не через локальный синк-push: «пройдено» считает сервер по
занятиям ВСЕХ преподавателей группы). Пройденное НЕ хранится, а считается
(`study_hours.hours_done`). План не задан → `total=0` и интерфейс не показывает строку
вовсе (не «24 из 0»).
⚠️ **Ключ плана содержит учебный период** (`hrs:Группа|Предмет|2025/2026|1`) — из-за
этого часы не появлялись в НАТИВНОМ журнале студента: сайт период подставляет всегда, а
экраны студента открывают `GradeBook(group, subject)` БЕЗ него и искали `hrs:…||0`, то
есть ключи не совпадали никогда. Теперь `core.GradeBook._hours_plan_keys()` при
отсутствии периода пробует ТЕКУЩИЙ термин (`terms.current_term()` — зеркало серверного
`webdata.current_term`), и лишь потом бестерминный ключ (там лежат строки, заведённые до
появления периодов). Журнал, открытый с ЯВНЫМ периодом (архив прошлого семестра), план
текущего НЕ подставляет — это была бы чужая цифра. Сама подпись «Пройдено X из Y ч» есть
теперь и в карточке предмета студента, и в шапке открытого предмета — на всех платформах
сразу, потому что экран один. Держат `tests/test_subject_hours_desktop.py`.

**Роль `parent`** (`server/app/routers/parent.py`, `ParentLink`, инвариант §13):
пять вкладок (журнал ребёнка, Вектор, сообщения, профиль, настройки), всё только чтение.
Вектор родителя собирает факты ОТ ЛИЦА РЕБЁНКА (переиспользует студенческий скоуп, чтобы
не отрастить вторую его копию), а тон задаёт `voice_role='parent'`.
Мессенджер: родитель невидим по построению (каталог работает по БЕЛОМУ списку ролей),
переписка — только с родителями своей группы и куратором, проверка стоит на СОЗДАНИИ чата
(`_guard_direct_allowed`), а не только в поиске. Группы/каналы он не создаёт.
На десктопе кабинет — та же SPA в окне WebView2 (нативной оболочки у роли нет и не было).

**Мессенджер:** добавлены системные каналы «Замены · Группа» (пост при правке ячейки
расписания; из ПАЧКИ правок — один пост на группу, иначе канал замьютят) и «Практика ·
Группа» (ведёт руками учебная часть — автоматики для практики в журнале нет).
**Три «умные» функции мессенджера (§17–19) — на GigaChat/Ollama из конфига админа, тем же
путём, что Вектор (`vector_llm.complete`). К озвучке (Silero) отношения не имеют.**
Общий код — `server/app/messenger_ai.py`.

- **§17 AI-поиск** (`GET /chats/{id}/messages/ai-search`). 🔑 Модель видит ТОЛЬКО поисковый
  ЗАПРОС и придумывает к нему словоформы и синонимы («домашка» → дз, задание); сопоставление
  с сообщениями делает сервер обычным вхождением подстроки. Переписка в модель НЕ уходит
  вообще. Настоящий семантический поиск (эмбеддинги + индекс) на одноядерном VPS с 960 МБ
  не поедет, а слать чужие сообщения в облако ради поиска нельзя — расширение запроса даёт
  основную пользу без обеих цен. Прямое совпадение весит больше синонима (`match_score`).
  Нет модели → `expanded` пуст и результат равен обычному поиску.
- **§18 AI-сводка** (`GET /chats/{id}/summary`). Только ПО КНОПКЕ: автосводка означала бы
  запрос к модели на каждый вход в чат. Здесь сообщения модели нужны по существу, поэтому
  ФИО маскируются ДО отправки (`messenger_ai.mask_names`, тот же приём, что у заметок
  «Избранного»). Кэш в памяти по ключу **(беседа, id последнего сообщения, его метка)** —
  метка в ключе не для красоты: id автоинкрементные, и после восстановления БД из бэкапа
  они выдаются заново, а кэш процесса это переживёт и отдал бы сводку чужого разговора.
  Модель недоступна → `summary=""` + `reason`, а НЕ выдуманный пересказ.
- **§19 Напоминания** — таблица `Reminder` (НЕ в SYNC_MODELS), разбор даты
  `reminder_parse.py` **без LLM** (та же причина, что у голосовой записи оценок: модель
  ошибается молча, а напоминание, съехавшее на день, хуже ненайденного). Текст храним
  СНИМКОМ — автор может отредактировать сообщение. Срабатывание СОБЫТИЙНОЕ, в
  `GET /me/events` (`_fire_due_reminders`): планировщик ради одной фичи — это вечный
  фоновый поток на одноядерном VPS, а проверка одной строки по индексу бесплатна.

Тесты — `server/tests/test_messenger_ai.py` (19 шт.): приватность обеих функций, границы
беседы и очищенной истории, поведение без модели, кэш, одноразовость напоминаний.
