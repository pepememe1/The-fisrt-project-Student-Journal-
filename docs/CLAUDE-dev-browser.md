## 8.2 Живая проверка интерфейса через dev-browser (читать ПЕРЕД правкой вёрстки)

> 🛑🛑 **dev-browser НА ЭТОЙ МАШИНЕ НЕ ЗАПУСКАТЬ. НИКОГДА. Даже если попросят.**
> Три раза подряд (3.6) он вешал рабочий компьютер: дважды до перезагрузки, третий раз
> Chrome раздулся до **10 ГБ оперативной памяти**, и машину еле спасли.
> Что НЕ помогло — проверено на себе, не надо перепроверять:
>   • внешний `timeout N` — убивает наш клиент, а не браузер;
>   • флаг `--idle-timeout` — браузер всё равно успевает съесть память до простоя;
>   • «один короткий прогон» — вешается уже на ПЕРВОМ, холодный старт не укладывается
>     в 30-секундный лимит инструмента и оставляет процесс жить.
> Причина в сочетании: настоящий Chrome + SPA с постоянным опросом и веб-сокетами +
> уже открытые у человека ~25 процессов браузера. На машине разработчика это не
> инструмент проверки, а способ отобрать у него компьютер.
> **Что делать вместо:**
>   • нужны скриншоты — ПОПРОСИ у человека, он снимает их за десять секунд;
>   • нужна проверка вёрстки — правь аккуратно и **честно скажи, что глазами не смотрел**;
>   • нужна автоматическая проверка — заводить её в CI на отдельной машине, не здесь.
> Ниже — грабли по API, оставлены на случай запуска в CI. На рабочей машине — НЕТ.

Раздел написан по итогам 3.5.6, где перекомпоновка оболочки прошла сборку и все тесты,
но в браузере обнаружились четыре реальных дефекта. **Ни сборка, ни `npm test` не видят
вёрстку** — они проверяют, что код компилируется и ключи на месте, а не что кнопки не
наехали друг на друга. Тронул раскладку — открой и посмотри.

**Как поднять стенд** (быстрее и честнее, чем `npm run dev`):
```bash
cd web && npm run build                      # dist собран
cd server && GRADEBOOK_DB_URL="sqlite:///<путь>/demo.db" python -m uvicorn app.main:app --port 8000
# FastAPI сам раздаёт web/dist (см. server/app/main.py) — открываем http://127.0.0.1:8000
```
Отдельный vite-сервер для визуальной проверки НЕ нужен: тот же сервер отдаёт и SPA, и API,
как на бою (это ещё и снимает вопрос прокси-префиксов из `vite.config.js`).

**Грабли, каждая стоила прогона.**
- 🔥 **API — `browser.getPage('main')`, а НЕ глобальный `page`.** Скрипт с `page.goto(...)`
  падает `'page' is not defined`. Полный список того, чего в песочнице нет, выдаёт
  `dev-browser --help`: `require`/`import`, `process`, `fs`/`path`/`os`, **`fetch`** и
  `WebSocket`, `__dirname`. Вход в аккаунт поэтому делается ИЗНУТРИ страницы
  (`page.evaluate(async () => fetch('/auth/login', …))`), а не из скрипта. Скриншот —
  `await saveScreenshot(await page.screenshot(), 'имя.png')`, вывод — `console.log`
  (значение из `return` наружу не печатается).
- 🔥 **НЕ ДОЛБИТЬ ПОВТОРНЫМИ ПРОГОНАМИ ПОСЛЕ ТАЙМАУТА.** 30-секундный лимит убивает
  СКРИПТ, но не браузер: живой Chrome остаётся крутить страницу с нашим опросом и
  сокетами. Три-четыре таких прогона поверх уже открытых вкладок пользователя и
  запущенного dev-сервера **подвесили рабочую машину целиком** (поймано вживую в 3.6).
  Правило: одна-две попытки, дальше ОСТАНОВИТЬСЯ, прибрать за собой и честно сказать,
  что визуальная проверка не выполнена. Прибирать так:
  `Get-Process *dev-browser*`, `Get-NetTCPConnection -LocalPort <порт стенда>` —
  и НИКОГДА не бить `Stop-Process -Name chrome` вслепую: там вперемешку браузер человека.
- 🔥 **`waitUntil: 'networkidle'` ВЕШАЕТ скрипт намертво.** У нашей SPA живой опрос
  (`messenger.loadChats` каждые 20 с), WebSocket мессенджера и HMR у vite — «сеть
  затихла» не наступает НИКОГДА. Окно открывается пустым (`about:blank`), скрипт молчит
  до таймаута, и выглядит это как «агент завис». Всегда `waitUntil: 'domcontentloaded'`
  + явный `waitForSelector`/`waitForTimeout`.
- **Скрипт исполняется в песочнице QuickJS, а не в Node**: `process`, `require`,
  переменные окружения и файловая система НЕДОСТУПНЫ (`'process' is not defined`).
  Параметры подставляй ГЕНЕРАЦИЕЙ файла скрипта (heredoc из bash), а не через env.
- ⚠️ **Один прогон — не дольше ~30 с**, дальше `Script timed out and was terminated`.
  Матрица «5 вьюпортов × 4 страницы» в один заход НЕ помещается: разбивай по одному
  вьюпорту (или паре страниц) на запуск. Браузер между запусками живёт, профиль и
  localStorage сохраняются — логиниться заново не нужно.
- 📁 **Скриншоты ложатся НЕ в текущую папку, а в `C:\Users\<user>\.dev-browser\tmp\`.**
  `page.screenshot({ path: 'ui-dash.png' })` кладёт файл именно туда; искать его рядом со
  скриптом бесполезно (потеряли время на `find /`). Оттуда же его и читать инструментом
  Read.
- `--headless` НЕ поддерживается (`unexpected argument`) — окно открывается настоящее.
- Установка (`npm install -g dev-browser && dev-browser install`) занимает несколько
  минут — запускай фоном и делай что-то ещё, а не жди.

**Что проверять машинно, а не глазами** (глаз пропустит, скрипт — нет):
```js
// Горизонтальная прокрутка body = что-то не влезло; список элементов за границей окна.
const de = document.documentElement, bad = []
for (const el of document.querySelectorAll('body *')) {
  const r = el.getBoundingClientRect()
  if (r.width > 0 && r.height > 0 && (r.right > window.innerWidth + 2 || r.left < -2)) bad.push(el.className)
}
return { hScroll: de.scrollWidth > de.clientWidth + 1, over: [...new Set(bad)].slice(0, 3) }
```
Плюс адресные инварианты под задачу: равная высота карточек в ряду
(`new Set(heights).size === 1` — ловит «лесенку»), непересечение fixed-элементов с
контентом (сравнить `getBoundingClientRect` вкладки и карточек), «карточка себя не уехала
из сайдбара» (`panel.bottom <= window.innerHeight`).

**Минимальный набор вьюпортов**: 1920 / 1440 / 1280 / 820 / 390 / 360. 1280 обязателен —
именно на нём ломается плотная сетка (на 1440 всё ещё хорошо, а на 1280 за вычетом
сайдбара на колонку остаётся ~170 px). Страницы: дашборд, Вектор, расписание (самая
плотная сетка), журнал (таблицы), настройки (длинная прокрутка) и мобильный drawer.

⚠️ **Демо-данные заводить прямо в БД** (`SessionLocal` + модели), а не через API:
`/auth/bootstrap-admin` на непустой базе отвечает 403, и это не баг. И **не подсовывать
боевую БД**: отдельный `GRADEBOOK_DB_URL` во временной папке, каталог должен
СУЩЕСТВОВАТЬ (sqlcipher не создаёт директории — падает `unable to open database file`).
